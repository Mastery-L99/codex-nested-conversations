# 安装、运行与更新验证

测试分成纯逻辑、隔离安装、目标应用三层。每层只支持相应结论；语法通过、工具握手或资源读取均不能代替实际页面操作和归档结果。

## 0.3.0-preview.5 桌面对话占用

发行包在独立的 Windows 测试目录完成安装检查。归档 ZIP 在空插件配置中通过官方 CLI 注册并安装，缓存中的 12 个插件文件与发行包逐一相符。完整安装器在普通路径和含空格的深路径各通过 76 项检查，涵盖安装、卸载及保留数据后的重装。两种下载包在 LF 和 CRLF 检出下分别构建，校验值一致。

使用同一合成会话和两个官方服务复现了写入占用。一个服务加载会话后，另一个仍能读取元数据，但归档返回 “already has an active writer”，记录保持未归档。随后让持有会话的服务执行归档，回读状态变为已归档。测试没有启动模型轮次。

本机正式桌面工具栏也完成了父子归档验收。先让当前桌面服务加载两条专用测试聊天，确认它们都处于空闲状态。工具栏只勾选父聊天，范围页显示这两条聊天，提交后显示“已归档 2 / 2 个对话”。最后独立回读，两条记录均已归档。

开发者可运行 `node scripts/test-archive-writer.cjs --output-dir <新的空目录路径>` 复现进程间占用。脚本要求目标路径尚不存在，并在其中创建隔离的合成数据和结果文件。

## 0.3.0-preview.4 后台范围检查

本节对应尚未发布的源码预览，当前官方包版本为 `26.1027.3384.0`。

预览四在真实桌面左上角入口完成只读检查。选择一个已有下级的父聊天后，确认框分别列出 16 个聊天和 16 条后台记录，每条后台记录均标明所属聊天。验收在确认页取消，没有提交该范围。

写入路径使用独立的临时 Codex 环境测试。官方程序处理了一套合成的父聊和后台子任务，只向父聊提交一次归档。两条记录的本机状态均从未归档变为已归档，任务结果分别核实普通聊天和后台记录各一条。

在预览二的官方桌面窗口中，从左上角“批量归档”选择已有验收父聊天，可看到两个下级标为“随上级归档”。再勾选其中一个子项后，确认页列出两条直接选择、三条唯一聊天。点击“归档全部 3 个”后，窗口显示已归档 3/3。后台记录确认先归档两个子项再归档父项，三条本机状态均为已归档。

独立归档后端已经使用本机官方 app-server 处理专用测试聊天。最新一轮在彻底停止原列表伴随模块后执行，操作前检查未归档，调用后读取本机状态确认已归档。对执行前已存在的全部聊天比较归档标记，只有该测试项从未归档变为已归档；后端不依赖侧栏适配器、调试连接或 Windhawk，也没有创建模型轮次。

本地插件先在空的隔离 `CODEX_HOME` 中完成来源添加、安装、工具发现和页面资源读取，随后安装到日常环境。官方桌面宿主中的新只读测试聊天已发现并调用 `open_archive_manager`，实际界面显示 MCP App、两个独立开关和当时的 159 条聊天目录。

独立页面的专用单项归档闭环已实机通过：筛选并勾选测试聊天、检查完整一项范围、返回修改后保留选择、再次检查并确认提交。界面显示已处理 `1/1`、已确认 `1`、失败 `0`；持久任务状态为 `completed`，提交与验证集合均只包含该测试项，不确定和范围外集合均为空。独立 SQL 读取显示该项已经归档。这一记录覆盖实际宿主中的单项成功流程；不能据此声称所有多级、停止和故障场景都已在同一页面逐项实操。

上述过程保持同一个官方主进程，没有重启客户端或更换登录环境。Windows 开机自启动状态仍为用户关闭，未安装 Windhawk。

原列表批量归档已用四条专用测试聊天检查筛选、选择、反选、跨筛选保留选择、完整范围取消、按后代优先提交和逐项归档状态。停止后检查本次停止请求的恢复结果、增强节点和被隐藏的原列表行。业务聊天未用于这组归档测试。

新模块的隔离测试覆盖：

- 独立开关的新鲜读取与合并、幂等更新、损坏设置保护、版本溢出、互斥锁占用及锁失效。
- 嵌套关闭后保留菜单桥接，归档关闭不影响嵌套；加载、检查、启用、释放任一步异常时继续初始化其他组件。
- 关系库缺失、损坏或改版，乃至嵌套读取脚本缺失、语法错误时仍返回平面目录。缺少主状态库时停止，不创建数据库；测试前后 SQLite 哈希一致，输出不含正文或私有路径。
- 一次性计划、过期、完整范围变更、隐式下级检查、串行执行、部分完成、停止、异常影响与中断恢复。
- MCP 参数类型、未知方法、工具可见范围、页面资源、消息来源与转义。页面保持自包含，空闲时不持续查询目录。

原图标加载的 Windhawk 路线仅有源码原型和离线检查。未安装服务，未完成引擎加载与原官方入口冷启动验收。ChatGPT 开机自启动保持关闭。

## 运行自动检查

在 Windows 上准备源码和锁定依赖：

```powershell
npm ci --ignore-scripts
npm run test:runtime
npm test
npm run audit:release
```

`test:runtime` 运行适用的模块、协议、页面和关系读取测试。页面测试使用合成内容和已安装的浏览器，不操作当前官方应用。安装测试只使用自己的临时目录，禁用快捷方式，不复制或启动另一份官方客户端。回收失败时保留现场并报错，不永久删除。

单独回归本次拆分边界：

```powershell
node --test tests/test-module-state.cjs tests/test-ui-modules.cjs tests/test-archive-catalog.cjs
node --test tests/test-archive-core.cjs tests/test-archive-app-server.cjs tests/test-archive-server.cjs
node tests/test-archive-panel.cjs
```

页面源码改动后，先执行 `npm run build:archive-panel`。独立插件清洁包通过 `npm run build:plugin -- --output-dir <新目录>` 生成；检查产物只含所需源码、页面、元数据和许可，不带开发依赖、官方资源、账户及运行数据。完整安装生成的 marketplace 只指向清洁 `plugin` 子目录，不能把包含依赖的安装根目录直接作为插件本体缓存。

受管理的安装测试可用 `CNCC_TEST_RECYCLE_SCRIPT` 指定已有回收脚本，参数为 `-LiteralPath`；默认用 `pwsh.exe` 执行，也可用 `CNCC_TEST_RECYCLE_HOST` 指定已安装的 PowerShell。未指定时使用项目自己的 Windows 回收实现。这些设置只用于测试目录清理。

## 目标宿主验收

只用明确命名的专用测试聊天执行写操作，先检查当前账户与目标范围。以下步骤分别记录客户端版本、模块版本和结果：

1. 在全新项目安装目录预演并安装，核对源码清单、独立数据位置和干净插件目录。重复安装必须停止；路径重解析点、修改过的快捷方式和无身份标记目录应保留。
2. 通过官方插件目录添加本地来源，在实际宿主打开归档页面，检查工具桥接、筛选、多选、范围确认、取消、进度和结果。单独的 CLI 安装记录不代替本步骤。
3. 在原列表适配器未运行、没有调试连接的情况下，用独立页面归档专用测试聊天，读取真实状态；再关闭嵌套开关重做，检查归档仍可用。
4. 关闭增强归档，检查不能再提交其任务；嵌套列表仍能展开、折叠。重新启用归档，检查另一个开关没有被覆盖。运行中关闭时，已提交项与尚未提交项分别反馈。
5. 模拟关系源不可读，检查平面列表保留、默认包含下级不会静默失效；用户手动改为只归档勾选项后才允许继续。让确认后的范围发生变化，执行应停止并要求重新检查。
6. 归档范围含多级关系、折叠下级和同名聊天，检查身份与完整清单；覆盖失败、停止及服务中断。官方接口的并发范围限制应在确认页可见，不宣称具有原子范围隔离。
7. 对原列表模块检查右键菜单与 `Ctrl+Shift+A`，确认准确当前聊天及全部已发现下级。快捷键被其他软件截获时先解决冲突；不增加备用全局键。
8. 停止原列表伴随进程，核对增强节点、隐藏行、事件与快捷键恢复，官方窗口继续可用，独立归档页仍可使用。停止恢复不完整时保持失败状态。
9. 先解除插件登记，再预演及执行项目卸载，核对程序和专用入口进入回收站、数据保留。回收失败立即停止。官方聊天、登录和开机自启动设置保持原状。
10. 正常退出官方应用并从原官方入口重开，分别记录默认原生列表、插件可用性和临时端点状态。原图标自动加载嵌套需要单独完成冷启动检查，不从其他入口的结果推断。

官方更新后重复受影响模块的检查。插件缓存刷新、源码发布和公共目录上架各自记录，不互相替代。

## 0.2.0-preview.1 历史实机记录

2026-10-30，旧版从全新的增强安装目录连接原官方应用和同一账户，首次生成关系数据并显示嵌套。停止后 `ownedNodes`、`hiddenFlat` 均为 0；卸载回收增强程序目录，保留独立数据。

旧版的开始菜单冷启动使用替换后的同名增强快捷方式，用户打开后看到嵌套。这个结果只覆盖该增强入口；官方“所有应用”、协议和自动启动仍可能绕过它。它不能证明原官方图标自动加载，也不包含本次独立归档插件。
